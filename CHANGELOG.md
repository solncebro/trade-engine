All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),

## [3.24.0] - 2026-10-03 — Ступени плеча рядом со спецификациями символов, слова биржи в отказе заявки, субсчета, журнал без потерь, Telegram целиком на telegram-engine

- **Округление на сетку символа получило направление.** `snapPriceToTick(symbol, price, rounding?)` и `snapAmountToStep(symbol, amount, rounding?)` принимают `'nearest'` (по умолчанию — поведение прежнее), `'up'` (не ниже значения) и `'down'` (не выше); тип `StepRounding` доступен из этого пакета (реэкспорт из exchange-engine). Снапперы `PriceTickSnapper` и `AmountStepSnapper` получают направление третьим аргументом — снаппер, поставленный вручную через `configurePriceTickSnapper` / `configureAmountStepSnapper` (бэктест, утилиты), должен его принимать. `ExchangeConnector.initialize()` прокидывает направление в `priceToPrecision` / `amountToPrecision` клиента биржи; своей математики сетки в пакете нет. `formatPrice` и `formatAmount` по-прежнему округляют к ближайшему шагу. Без снаппера или для символа без фильтров значение возвращается как есть, при любом направлении. Нужна exchange-engine 0.26.0. Повод — rubber 01.10.2026: цена ручной заявки на продажу поднимается на сетку ВВЕРХ, чтобы заявка не встала ниже плановой цены. (`src/utils/priceFormat.ts`, `src/utils/numberFormat.ts`, `src/utils/numberFormat.types.ts`, `src/services/exchangeConnector.ts`, `tests/priceFormat.test.ts`, `tests/numberFormat.test.ts`)

- **`PersistedListDocument<TRecord>`** — список записей по ключу в памяти, фоном зеркалируемый в один документ (обычно соседний документ Firebase): документ хранит список, непрочитанный документ не переписывается, поздно прочитанный сливается с памятью (память главнее, забытое за время непрочитанности не возвращается), залп изменений схлопывается в одну запись, повтор каждые 30 с на таймере, не держащем процесс, `flush()` перед остановкой. Повод — rubber: один и тот же механизм был скопирован в две памяти (сетапы входа и последние сетапы).

- **Режим позиций фьючерсного счёта во время работы.** `PositionManager.setPositionMode({ mode })` переключает счёт между «одна позиция на символ» и хеджем (лонг и шорт одного символа одновременно) и с этого момента строит все заявки под новый режим; `PositionManager.readPositionMode()` — режим, как его сообщает биржа (`undefined` — биржа не может сказать: Bybit выводит его из позиций). `ExchangeConnector.futuresPositionMode` теперь не поле только для чтения, а геттер; `adoptFuturesPositionMode(mode)` — принять режим без обращения к бирже (например прочитанный при запуске). Повод — telegram-signals-trade: у трейдера по одной монете одновременно покупка и шорт, режим включается выключателем трейдера. Биржи отказывают в смене режима, пока на счёте есть позиция или заявка, — переключает вызывающий только на пустом счёте. Нужна exchange-engine 0.26.0 с монетой расчётов в смене режима Bybit.

- **`OrderManager.enqueueOpenPositionMarket`** — открывающая рыночная заявка с собственным номером вызывающего, в очереди позиции наравне с остальными заявками; ответ `{ isSuccess, orderId, errorText }`, отказ не бросает. Повод — вход «по рынку сейчас» у трейдера, после объявления которого цена сразу уходит.

- `readCapitalBase`: баланс субаккаунта читается только по считаемой монете (`assetList: [asset]`). Причина — единый счёт Bybit отклоняет чтение без списка монет (живой ответ 26.09.2026, ошибка 131203); нужна exchange-engine 0.26.0 с полем `assetList`.

- `FirebaseServiceBase`: параметр `wholeMapFieldList` — поля с набором элементов (например трейдеры), которые при запуске дописываются из значений по умолчанию только целиком, если поля нет, и никогда не по одному элементу. Причина: иначе элемент, удалённый пользователем, возвращался в документ при каждом перезапуске (telegram-signals-trade, удаление трейдера из бота).

Выпуск собран из нескольких поводов. Первый — AVAUSDT на Bybit 17.09.2026: потолки ступеней плеча
нужно знать до отправки заявок, а отказ биржи — читать её словами. Второй — приложение копирования
сделок из Telegram: ему нужны разбор имени монеты «как напишут», плечо, при котором ликвидация
дальше стопа, субсчета и база капитала «главный счёт + все субсчета».
Третий — обвязка, скопированная в шесть-семь приложений (чтение окружения, остановка, очереди,
журнал, Firebase), переехала сюда. Четвёртый — требование владельца: весь Telegram в этом пакете
идёт через `@solncebro/telegram-engine`, своих реализаций не остаётся.

**Порядок публикации:** сначала `@solncebro/telegram-engine` 0.6.0 и `@solncebro/exchange-engine`
0.26.0, затем этот пакет — он требует обе версии как минимальные.

### Added

- **`describeError(error)` — единственный помощник «ошибка → текст».** Экспорт из пакета
  (`src/utils/errorFormatter.utils.ts`): у `Error` берёт сообщение (пустое — `toString()`), у объекта
  с полем `message` — его, остальное приводит к строке (`null`/`undefined` → «Unknown error»).
  Причина: строчка `error instanceof Error ? error.message : String(error)` жила отдельной копией в
  каждом файле каждого приложения (в одном telegram-signals-trade — 12 копий) и десятком копий
  внутри этой библиотеки; `describeExchangeRefusal` теперь читает ошибку тем же способом и
  остаётся как имя для слов биржи. **Правило для приложений на этой версии:** своих
  `describeError` / `getErrorMessage` / встроенных `instanceof Error ? …` больше не заводить —
  импортировать `describeError` отсюда (см. `.claude/rules/code-conventions.md`).

- **Память ступеней плеча в коннекторе.** `ExchangeConnector` держит ступени плеча по символу
  (`LeverageTier` из exchange-engine 0.26.0): загружает их в `initialize()` сразу за спецификациями
  инструментов (сбой — предупреждение в лог, старт не прерывается), перечитывает тем же суточным
  пересмотром инструментов в 00:05 UTC, догружает по требованию —
  `ensureFuturesLeverageTierListLoaded(symbol, isForced)`: символ, которого не было в общем чтении
  (свежий листинг), читается один, одновременные вызывающие делят одно чтение, пустой ответ биржи
  не переспрашивается минуту, а `isForced` перечитывает и уже известный символ (для приложения,
  которому отказ биржи доказал, что таблица устарела). Чтение — `getFuturesLeverageTierList(symbol)`,
  без сети. Повод — AVAUSDT на Bybit 17.09.2026: потолок ступени при плече 5× — 5000 $, план входа —
  10000 $; приложению нужно знать потолки ДО отправки заявок, а не по отказу.
- **Коннектор без ключей не читает ступени плеча подписанным запросом.** Коннектор только для открытых
  рыночных данных (пустой ключ или пустой секрет) на бирже, где таблица ступеней отдаётся лишь с подписью
  (Binance, `/fapi/v1/leverageBracket`), общее чтение и догрузку по символу пропускает: ступеней у него нет,
  `ensureFuturesLeverageTierListLoaded` отвечает `false`, в лог — одна строка уровня отладки. Bybit и OKX отдают
  ступени без ключа и читают их как раньше. Повод — приложение копирования сигналов из Telegram: коннектор
  Binance без ключей при запуске писал ошибку 401 «API-key format invalid».
- **Символ из ввода человека или сигнала — одним вызовом.** `parseRawSymbolInput(raw)` превращает «$pepe», «#BTC»,
  « btc », «BTC/USDT», «BTCUSDT.P», «PEPE/USDT:USDT», «1000PEPE» в имя вида `PEPEUSDT` (без котировки дописывает USDT),
  а `ExchangeConnector.resolveFuturesSymbol(raw)` / `resolveSpotSymbol(raw)` доводят его до имени на бирже и отвечают
  `{ symbol, isFound }`: приставка 1000 по тикерам, множитель после основы, как у Bybit (`SHIB1000USDT`), и догрузка
  спецификации только что вышедшей монеты. Прежний `resolveSymbolWithPrefix` не менялся; рядом —
  `findSymbolWithPrefix`, который промах отдаёт как `null`, а не как исходное имя. Повод — четыре собственные копии
  разбора ввода в приложениях (volume-breaker, ma-chaser, market-data-feeder, kliner) и приложение копирования сигналов
  из Telegram, где имя монеты пишут как угодно; живая проверка на Bybit показала, что `shib` без суффиксного поиска
  не находился вовсе.
- **`ExchangeConnector.waitForTickersReady(timeoutMs)`.** `initialize()` запускает кэш тикеров без ожидания, поэтому
  поиск приставки сразу после старта смотрел в пустой кэш и не находил `1000PEPEUSDT`. Метод ждёт первый снимок
  (по умолчанию до 30 с), никогда не бросает и отвечает `false`, если снимок не пришёл; `resolveFuturesSymbol` ждёт сам.
- **Плечо, при котором ликвидация дальше стопа.** `computeMaxLeverageBeforeStop` — наибольшее целое плечо, при котором
  цена ликвидации изолированной позиции лежит за стопом с запасом в процентах; обслуживающая маржа — числом в процентах
  или по ступеням плеча символа (ступень выбирается по размеру позиции, её потолок плеча соблюдается).
  `estimateIsolatedLiquidationPrice` — сама формула (опубликованные формулы Binance и Bybit для изолированной маржи;
  что приближено — в комментарии). `resolveEntryLeverage` — итоговое плечо входа: плечо сигнала или по умолчанию →
  сторож стопа → `fitLeverage` по потолкам ступеней, с причиной. Повод — правило копирования сделок: плечо сигнала
  или 5, но ликвидация обязана наступать после стоп-лосса.
- **`fitLeverage` в библиотеке** (перенос из rubber вместе с тестами): плечо, при котором потолок ступени вмещает весь
  план входа, с понижением по свободной марже. Нужен не только rubber — любому приложению с входом крупнее первой ступени.
- **Баланс счёта одной функцией.** `readAccountBalance(connector.futures)` → всего / свободно / занято в долларах
  (занятая маржа читается у биржи, не вычитается), `readFreeMarginUsd`, `readSpotQuoteBalance({ client: connector.spot })`
  — монета расчёта спота. Непрочитанный баланс — `null`, а не ноль. Перенос из rubber.
- **`computeBreakevenWithFees(avgEntry, feePercent, direction)`** — безубыток с комиссией входа и выхода, комиссия в
  процентах. Перенос из volume-breaker, где функция была закрыта внутри стратегии.
- **Срок действия лимитной заявки.** `OrderParams.timeInForce` и одноимённое поле у `openPositionLimit`,
  `closePositionLimit`, `openPositionBatchLimit`, `closePositionBatchLimit`, `OrderManager.enqueueCreateLimitOrder` и
  `enqueueMoveLimitOrder` — например `PostOnly`, «только в стакан». Не задано — как раньше «до отмены»; рыночная
  заявка всегда «исполнить и отменить остаток». `isPostOnlyRejection({ errorCode, rejectReason })` узнаёт отказ
  «заявка встала бы по рынку»: Binance фьючерсы — код -5022, Bybit — причина `EC_PostOnlyWillTakeLiquidity` в потоке
  заявок (оба по официальной документации).
- **Закрывающая лимитка в очереди заявок.** `OrderManager.enqueueCreateLimitOrder` / `enqueueMoveLimitOrder` получили
  `isReduceOnly` (заявка только уменьшает позицию, `direction` — направление ПОЗИЦИИ) и отдают `errorCode` отказа
  биржи. Повод — приложению копирования сделок нужны закрывающие лимитки (тейки) через ту же очередь.
- **`UserDataStreamRouter` — один личный поток счёта на всех потребителей.** Нижняя библиотека держит один набор
  обработчиков на клиента; второй потребитель вытеснял первого. Роутер подключается один раз
  (`connector.getUserDataStreamRouter()`), раздаёт события заявок, позиций и баланса всем подписчикам, ошибка одного
  (в том числе отказ его обещания) не мешает остальным, а об обрыве и возврате потока сообщает событиями
  `onConnectionLost` / `onConnectionRestored` / `onResyncRequired` (события за время обрыва потеряны — перечитать
  состояние). Обрыв и возврат приходят от exchange-engine 0.26.0; роутер описан её собственными типами.
- **Общие рыночные данные для главного счёта и субсчетов.** `connector.shareMarketDataFrom(primary)` до `initialize()`:
  коннектор той же биржи и того же режима (демо/боевой) берёт у главного список инструментов, тикеры и ступени плеча,
  а не грузит их сам. Пять коннекторов одной биржи раньше читали всё это пять раз, тикеры — каждые 30 секунд.
  Заявки, позиции, баланс, плечо, очередь записи и личный поток остаются у каждого счёта свои. Без вызова поведение
  прежнее. Живая проверка на Bybit: ведомый коннектор стартовал за 1 мс, ни одного собственного чтения, 891 символ
  как у главного.
- **Субсчета через библиотеку.** `connector.subAccounts` (`SubAccountGateway`) — операции ключа главного счёта:
  `listSubAccounts()`, `transferToSubAccount(...)` / `transferFromSubAccount(...)` с номером перевода вызывающего
  (`transferId`, UUID годится обеим биржам), `fetchTransferStatus(...)`, `fetchSubAccountBalanceList(...)`. Ответ —
  результат с `isSuccess`, отказ несёт слова биржи в `errorText` и код в `errorCode`, ничего не бросается. Перевод
  библиотека не повторяет никогда: потерянный ответ не говорит, ушли ли деньги, — вызывающий спрашивает состояние
  по тому же номеру. В демо-режиме и на OKX нижняя библиотека отказывает без выхода в сеть — такой отказ помечен
  `isNotSupported: true`. Перечисления `WalletTypeEnum`, `SubAccountStatusEnum`, `SubAccountTransferDirectionEnum`,
  `SubAccountTransferStatusEnum` и все типы подсчётов отдаются из этого пакета. `readCapitalBase({ masterClient,
  subAccountGateway, subAccountIdList })` — «база капитала = главный счёт + все субсчета»: реализованный (кошельковый,
  без плавающего результата) остаток USDT, сложенный по всем счетам; если хоть один счёт не прочитан, итог `null`, а
  не заниженная сумма. Повод — приложению копирования сделок нельзя обращаться к exchange-engine напрямую, а субсчета
  появились только там.
- **Журнал сделок больше не теряет строки при сбое базы и перезапуске.** Новый необязательный параметр
  `PersistentTradeJournalConfig.spoolFilePath`: всё, что Supabase не принял после всех повторов — и сводки, и
  события, — дописывается в файл на диске (одна запись на строку) и досылается при `initialize()` и после
  следующего удачного слива. Повторная досылка безопасна: сводки перезаписываются по ключу (свежая версия из
  памяти всегда важнее копии с диска), события, уже лежащие в базе (тот же ключ сделки и тот же номер по порядку),
  пропускаются. Файл только дописывается и удаляется лишь после подтверждения базой; частичный успех
  переписывает его через временный файл и переименование. После перезапуска счётчики номеров событий продолжаются
  с файла, а `rehydrateSummaries` берёт из файла более новую версию сводки. Без параметра — всё как раньше.
  Повод — раньше при окончательном сбое записи события выбрасывались (так было задумано, чтобы очередь не росла
  бесконечно), а всё несохранённое жило только в памяти и пропадало при падении процесса; приложению нужно
  «никогда не терять данные» через перезапуски, обрывы сети и сбои Supabase.
- **Именованные листы Google Sheets.** `PersistentTradeJournalConfig.sheetTargetList` — список
  `{ sheetName, shouldIncludeRow(row) }` (тип `JournalSheetTarget`): живое зеркало, сверка и полная
  перезапись пишут каждую строку во все листы, которым она подходит («Сделки» — все строки, лист на каждого
  трейдера — его строки); недостающий лист создаётся с заголовком. `journal.replaceNamedSheet(sheetName, rowList)`
  и отдельная `replaceSheetValues(...)` целиком переписывают лист готовой таблицей — для «Сводки». Без списка
  листов — прежняя запись в первый лист. Повод — зеркало умело писать только в первый лист книги.
- **Supabase: общий клиент и загрузка файлов.** `createSupabaseServiceClient({ url, serviceKey })` — тот же
  способ создания клиента, что внутри журнала (журнал теперь им и пользуется), `journal.getSupabaseClient()`
  отдаёт уже созданный клиент. `uploadFileToStorage({ client, bucket, path, content, contentType, isUpsert,
  signedUrlExpiresInSeconds? })` кладёт файл (картинку сделки) в Supabase Storage с повтором через
  `withResultRetry` и возвращает путь, публичную и, по просьбе, подписанную ссылку; ошибка не бросается, а
  приходит полем `errorText`. Повод — картинки сделок хранятся в Supabase Storage, а клиент журнала был закрыт.
- **Firebase: подписка сама поднимается, настройки переживают недоступность Firestore.** В `FirebaseServiceBase`
  (все новые параметры необязательны, прежний вызов конструктора работает):
  - ошибка живой подписки больше не убивает её навсегда: подписка переоткрывается с растущей паузой
    (`resubscribeInitialDelayMs` / `resubscribeMaxDelayMs`, 1 с → 60 с);
  - сторож снимка `snapshotWatchdogIntervalMs` (по умолчанию выключен): периодически перечитывает документ и
    сравнивает с копией в памяти; при расхождении чинит копию, шлёт `dataChanged` и `snapshotDiverged`,
    переоткрывает подписку и один раз на эпизод присылает уведомление (перенесено из ma-chaser, починка кэша —
    как в kliner); публичный `checkSnapshotFreshness()` для проверки по требованию;
  - `snapshotCacheFilePath`: последняя хорошая копия документа на диске; если Firestore недоступен при старте,
    сервис стартует с неё (событие `startedFromDiskCopy`, уведомление с временем копии) вместо падения и
    продолжает пытаться подключиться (`connectionRetryIntervalMs`, 30 с); первое чтение ограничено
    `initialReadTimeoutMs` (30 с), только когда копия на диске задана;
  - события `connectionLost` / `connectionRestored` и `isConnected()`; имена событий — `FIREBASE_SERVICE_EVENT`;
  - записанное через `updateData` значение видно в `getData()` сразу, не дожидаясь эха Firestore
    (`isWriteVisibleImmediately`, по умолчанию включено; `pendingWriteMaxAgeMs`, 15 с) — перенесено из rubber и
    доработано для вложенных настроек (слияние по пути, а не замена целой ветки);
  - соседние документы `readSiblingDocument(name)` / `writeSiblingDocument(name, data)` (из rubber);
  - карта элементов внутри документа: `setMapItem(location, itemId, value)`, `updateMapItem(location, itemId,
    partial)`, `removeMapItem(location, itemId)` (из ma-chaser saveChaser/updateChaser/removeChaser); `location` —

  Повод — ни одна библиотека этого не умела, каждое приложение (rubber, ma-chaser, kliner) держало свою копию,

  через проксированный клиент, поэтому сторож стакана (если включён) обёртывает обработчик
  трекера как любой другой.
- **`sliceAskVolumeWithinBand({ askList, referencePrice, bandPercent, remainingQty })`**
  (`src/utils/orderBookSlice.ts`) — чистый срез: сколько можно купить разом, не заплатив выше
  `referencePrice × (1 + bandPercent/100)`. Полоса отсчитывается от ОПОРНОЙ цены, не от
  текущей лучшей: если лучшая уже на +0,3 %, полоса 0,5 % допускает только объём между +0,3 и
  +0,5 %, а лучшая за границей даёт `isBeyondBand`. Никакого доступа к бирже — пригодна любому
  боту, который режет рыночную заявку по глубине.
- **`sleep(ms)`** экспортируется из пакета (`src/utils/sleep.ts`) — одна пауза на библиотеку
  и её потребителей.
- **`KlineWatchdogStrategy`** (`src/services/klineWatchdogStrategy.ts`) — клайны как стратегия
  общего `StreamSubscriptionWatchdog`: возраст по проекции интервала с масштабируемым допуском,
  восстановление одной пакетной переподпиской на всю пачку плюс REST-дочитка и реплей в
  обработчик, форматирование сообщений по интервалам — всё, что раньше лежало в отдельном
  классе. У `StreamWatchdogStrategy` появились необязательные хуки: `computeGraceMs(key,
  default)`, `prepareRecoveryBatch(keyList)`, `formatOverdue(...)`, `formatScanResult(...)`,
  `describeStartup()`; `recover(key, context)` получает последнюю отметку свежести, результат
  может нести `freshnessTimestamp` и `replayedCount`, а события здоровья — `replayedCount` и
  `consecutiveFailCount`. `registerKey(key, freshnessTimestamp?)` принимает посев свежести.

### Changed

- **`KlineSubscriptionWatchdog` — тонкая обёртка** над `StreamSubscriptionWatchdog` +
  `KlineWatchdogStrategy` с ПРЕЖНИМ публичным интерфейсом (`wrapHandler`, `unregisterHandler`,
  `start`, `stop`, `getDiagnosticInfo`, хуки `onStreamStale/Recovered/RecoveryFailed` с

## [3.21.0] - 2026-08-25 — Одна копия слоя связи и канала в процессе потребителя

Помечено минорной версией, а не патчем: раньше точная версия зависимости не давала
транзитивной версии сдвинуться без переиздания этого пакета — теперь диапазон открыт, и
следующий выпуск слоя связи или канала подтянется к потребителю без апгрейда trade-engine.
Кода это не касается, но раньше договор был «версию транзитивной зависимости меняет только
релиз trade-engine», а теперь это может сделать любая установка пакетов.

### Changed

- **Зависимость от `@solncebro/exchange-engine` записана открытым диапазоном
  `>=0.22.0 <1.0.0` вместо точной версии `0.22.0`.** Точная версия гарантирует дубль в тот момент, когда у потребителя
  оказывается любая другая: установщику некуда деваться, кроме как вложить вторую копию слоя
  связи внутрь этого пакета. Именно так rubber пришёл к тому, что путь рыночных данных
  обслуживал слой связи 0.18.3 (прибитый оркестратором 3.14.0), пока путь ордеров работал на
  0.22.0 — один процесс, два слоя связи, две тиковые сетки цен и два реестра условных заявок,
  и половина исправлений не видна той половине, которая торгует. Диапазон намеренно открыт вверх до 1.0.0, а не заперт в ветке 0.22: у пакетов младше
  единицы «крышечка» не переходит через минорную версию, поэтому каждый минорный выпуск слоя
  связи требовал бы перевыпуска этого пакета ради одной цифры — и, пока он не вышел, у
  потребителя снова лежали бы две копии слоя связи.
- **Объявлен `@solncebro/websocket-engine` (`>=0.6.0 <1.0.0`).** Сам оркестратор канал не
  импортирует — он объявляет его как ПОСТАВЩИК: начиная с 0.22.1 слой связи требует канал
  одолженной зависимостью и своей копии больше не заводит. Благодаря этому ни одному торговому
  приложению не нужно ничего менять у себя: канал приходит вместе с оркестратором, и в процессе
  он ровно один.

## [3.20.0] - 2026-08-18 — Диапазон в выборке журнала и правильный порядок листа

### Added

- **`PersistentTradeJournal.selectRows` принимает `range` и `order`** (`JournalSelectRangeArgs` —
  экспортируется из пакета): полуоткрытый отрезок по одной колонке (`fromValue` включительно,

  тасовала весь лист заново. Не задано — поведение не меняется, используется прежний

## [3.14.0] - 2026-08-04

### Added

- **Модуль определения тренда (`TrendCalculator` + `TrendMonitor`)** — определяет направление (рост/падение/боковик) и численную силу (0–100) тренда актива по закрытым свечам методом структуры рынка (вершины и впадины, метод Доу). `TrendCalculator` — статический расчёт: поиск вершин/впадин зигзагом с адаптивным от волатильности порогом (`computePivotList`); вердикт по последним точкам с досрочным сломом тренда по закрытию за уровнем последней противоположной точки (`assessTrend`); сила из трёх составляющих (согласованность шагов, крутизна, мелкость откатов). `TrendMonitor` — живой наблюдатель поверх источников свечей: держит вердикт по каждому интервалу отдельно и сводку по всем, шлёт событие `trendChanged` только при фактической смене направления по закрытой свече, чисто снимает подписки. `formatTrendSummaryMessage` — готовый текст сводки для Telegram. Модуль ничего не торгует, не отправляет сам и не ходит на биржу — только отвечает и оповещает. (`src/core/trendCalculator.ts`, `src/core/TrendMonitor.ts`, `src/telegram/trendMessageTemplates.ts`, `.claude/rules/trend.md`)

  Доработки по итогам ревью на реальных данных: (1) множитель порога по умолчанию `1.618` (был 2 — слишком грубо, «замораживал» структуру на сильных движениях); (2) потолок порога `maxReversalPercent` (20%) — одна вертикальная свеча с огромным истинным размахом больше не раздувает ATR настолько, что реальный откат после неё перестаёт считаться разворотом; (3) слом тренда проверяется по **всей** истории после впадины/вершины, а не только по последней свече; (4) новые поля `TrendAssessment.trendStartIndex`/`trendEndIndex` — границы текущей структурной ноги (самый недавний монотонный отрезок higher-high+higher-low, ломающая точка в него не входит; считается и при `flat`), чтобы нумеровать точки от реального начала тренда, а не от края данных; `isYoungAfterBreak` (тренд стартовал сразу после структурного слома — сила ×0.5); (5) соседние точки гарантированно на разных свечах; (6) потолок порога `maxReversalPercent` (20%) против раздувания ATR одной вертикальной свечой; (7) множитель порога по умолчанию `1.618`.

- **`KlineSubscriptionWatchdogConfig.graceScaledIntervalList`** — список таймфреймов, для которых запас просрочки масштабируется длиной свечи: порог = `openTimestamp + intervalMs + (intervalMs + graceMs)`, то есть тревога только после пропуска ДВУХ свечей подряд. Для таймфреймов вне списка формула прежняя (`openTimestamp + intervalMs + graceMs`); по умолчанию список пуст, поэтому поведение существующих потребителей не меняется. (`src/services/klineSubscriptionWatchdog.ts`, `klineSubscriptionWatchdog.types.ts`)

  Повод — постоянные ложные тревоги «Kline subscriptions overdue … 5m — Lag 184s» по единичным неликвидным символам в kliner. Сторож считает свежесть по времени ОТКРЫТИЯ последней полученной свечи, а по неликвидному символу внутри 5-минутки может не прийти ни одного обновления: самым свежим остаётся открытие предыдущей свечи, и при запасе (180с) меньше длины свечи (300с) тревога срабатывала гарантированно, стоило первым трём минутам новой свечи пройти без сделок. Каждая такая ложная тревога тянула за собой переподписку и REST-рефетч истории. Замер по бирже (сутки минутных свечей): паузы без сделок до 3–11 минут по разным символам, у части монет встречаются пятиминутки вовсе без сделок.

### Fixed

- **Зеркало журнала в Google-таблице: числа записываются числами, а не текстом.** Корень обоих дефектов (даты показывались голым числом вместо даты; в ячейке виднелся весь хвост двоичной арифметики) — зеркало формировало КАЖДУЮ ячейку строкой, а `valueInputOption: USER_ENTERED` разбирает такую строку по языку САМОЙ таблицы. У боевых таблиц rubber язык `ru_RU` (десятичный разделитель — запятая), поэтому «46233.04166666667» числом не признавалось и ячейка молча становилась текстовой: оформление «дата-время» к тексту неприменимо, а текст показывает ровно то, что в нём лежит. Проверено чтением ячейки боевой таблицы: `userEnteredValue.stringValue`. Теперь числовые значения уходят числами, остальное — текстом; сравнение «лист против базы» приводит обе стороны к тексту, поэтому строки не переписываются вхолостую. (`src/services/tradeJournal/sheetsSync.ts`)

- **Числа в таблице без мусорного хвоста двоичной арифметики.** Проценты уходят в лист делением на 100, и −2,83 давало −0,028300000000000002. Значения приводятся к 15 значащим цифрам — хвост исчезает, настоящие длинные числа (средневзвешенная цена входа вида 0,00619640833333333) сохраняются полностью, и значение переживает цикл «запись → чтение» без изменений. (`src/services/tradeJournal/sheetsSync.ts`)

- **Оформление даты переставляется после каждой дописки строк** и после полной перезаписи листа, а не только при подключении: строка, добавленная вставкой (`insertDataOption: INSERT_ROWS`), оформление колонки не наследует. Значение даты остаётся дробным — по документации Google целая часть числа это дни с 30.12.1899, дробная — время суток, поэтому округлять его до целого нельзя (потерялось бы время сделки). (`src/services/tradeJournal/sheetsSync.ts`)

## [3.12.0] - 2026-07-15

### Added

Появился после инцидента 15.07.2026: фидер на проде не был перезапущен после фикса 3.11.0, и rubber всю сессию торговал акциями (SNDK/SOXL/SNXX) — теперь приложение-приёмник отбрасывает их само. (`src/services/tradifiSymbolGate.ts`)

- **`splitOrderQty({ rebalanceTail })`** — новая опция канонического дробителя объёма: когда остаточный хвост меньше minQty, последний кусок ужимается так, чтобы хвост дорос до minQty, вместо молчаливого отбрасывания. Хвост округляется по шагу ВВЕРХ, ужатый кусок — ВНИЗ (сумма кусков никогда не превышает исходный объём — критично для reduce-only заявок); невыполнимо (ужатый кусок упал бы ниже minQty) — прежнее поведение с отбрасыванием, вызывающий видит недостачу по сумме кусков. Нужна защитным и закрывающим заявкам: отброшенный хвост стопа = вечно незакрываемая пыль позиции (инцидент BLASTUSDT 15.07.2026: биржевой потолок рыночной заявки молча урезал стоп 53.4М контрактов до 43М, остаток повис без защиты). (`src/utils/sizeOrder.ts`)

### Fixed

Остаток меньше одного шага количества теперь считается нулём — он всё равно непредставим в заявке. (`src/utils/sizeOrder.ts`)

## [3.5.0] - 2026-05-17

### Added

**Reliability-инфраструктура**:
- **`RateLimitedRequestQueue`** (`src/core/RateLimitedRequestQueue.ts`) — sliding-window очередь для write-операций с заданным RPS. Args: `{ rateLimit, intervalMs?, loggerLabel? }`. Логирует первый throttle.
- **`withRetryOn429`** и **`withReadRetry`** (`src/core/withRetryOn429.ts`) — функциональные retry-обёртки на 429/5xx с exponential backoff и поддержкой `Retry-After`. Args: `{ fn, contextLabel, maxRetries?, baseDelayMs? }`.
- **`KlineSubscriptionWatchdog`** (`src/services/klineSubscriptionWatchdog.ts`) — мониторинг и автоматическое восстановление потерянных kline-подписок. Periodic scan → resubscribe → REST refetch + replay user handler. API диагностики `getDiagnosticInfo()`.

**ExchangeConnector**:
- 5-й и 6-й аргументы конструктора: `klineWatchdogConfig?: KlineSubscriptionWatchdogConfig` (опциональный мониторинг) и `rateLimitConfig?: RateLimitConfig | null` (override rate limit).
- При `initialize()` динамически опрашивает `getOrderRateLimit()` и создаёт `RateLimitedRequestQueue` для write-операций (используется через `PositionManager`).
- `loadTradeSymbols` и `fetchTickers` теперь обёрнуты в `withReadRetry`.
- Геттеры `spot` и `futures` возвращают Proxy с watchdog-обёрткой `subscribeKlines`/`unsubscribeKlines` (если watchdog включён).

**PositionManager** (расширения 3.5.0):
- **`cancelAllOrders(args: CancelAllOrdersArgs)`** — высокоуровневая обёртка над `client.cancelAllOrders(symbol)` с queue+retry.
- **`cancelBatchOrders(args)`** теперь возвращает `Promise<CancelBatchOrdersResult>` (per-order результаты `{ orderId, isSuccess, errorCode, errorText }`).
- **`modifyOrder(args: PositionManagerModifyOrderArgs)`** — высокоуровневая модификация одного ордера (price/amount/triggerPrice).
- **`modifyBatchOrders(args: PositionManagerModifyBatchOrdersArgs)`** — массовая модификация ордеров (Binance Futures REST chunk=5, Bybit linear=20 / spot=10; Bybit через WS если подключён). На Binance Spot бросает `Not supported for spot market`.
- Все write-операции (open/close/cancel/modify/setLeverage/setMarginMode) теперь идут через `withRetryOn429` и write-очередь.
- Constructor принимает опциональный `queue?: RateLimitedRequestQueue`. Если не передан, очередь берётся у `ExchangeConnector` (`getWriteQueue()`) **на каждый вызов** — гарантирует актуальный RPS из `initialize()` (раньше очередь фиксировалась при первом обращении к `positionManager` и могла навсегда остаться на fallback).

**FirebaseServiceBase**:
- `updateData(data)` теперь корректно обрабатывает вложенные объекты через внутреннюю утилиту `flattenForFirestoreUpdate()` — превращает `{ a: { b: 1 } }` в `{ "a.b": 1 }` (dot-notation, как требует Firestore `documentReference.update()`).

### Fixed (релиз-ревью 3.5.0)

- **`KlineSubscriptionWatchdog.stop()`** очищает все внутренние коллекции (`subscribedHandlerByKey`, `subscribedIntervalByKey`, `lastKlineByKey`, `recoveryStateByKey`, `suppressedKeySet`) — ранее `subscribedHandlerByKey`/`subscribedIntervalByKey`/`lastKlineByKey` оставались, и после `stop()`+`start()` старые подписки сразу считались overdue и реплеились в устаревшие хендлеры.
- **`PositionManager`** больше не фиксирует write-очередь при первом обращении: берёт её у `ExchangeConnector.getWriteQueue()` на каждый вызов, поэтому write-операции, выполненные до завершения `initialize()`, после него используют актуальный RPS (раньше могли навсегда остаться на fallback).
- **`withRetryOn429`** учитывает заголовок `Retry-After` не только на `429`, но и на `5xx` (биржевые maintenance-окна отдают `Retry-After` на `503`) — раньше на `5xx` всегда применялся exponential backoff.
